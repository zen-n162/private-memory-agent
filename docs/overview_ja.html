Local-first personal memory AI

Private Memory Agent

Private Memory Agent は、ユーザー自身の写真、LINE エクスポート、ノートを ローカル環境で扱い、根拠を示しながら質問に答えるための AI エージェントです。

このページは説明用の静的 HTML です。実在の個人データ、実際の LINE 文面、 ノート本文、写真ファイル名、GPS 座標、秘密情報は含めていません。

このアプリでできること

記憶を探す 日付、人、場所、話題、イベントを手がかりに、ローカルの記録を検索します。
何があったか説明する 写真、LINE、ノートの証拠を組み合わせ、できる範囲で出来事を説明します。
根拠を表示する 回答だけでなく、どの証拠を使ったかを evidence id と安全なスニペットで示します。
不確実性を述べる 証拠が弱い場合は断言せず、分からない点を明示します。
根拠のない主張を避ける 検索された証拠に基づかない結論を出さない方針です。
ローカルで動かす 既定では外部 API に送信せず、手元の設定とローカルモデルを前提にします。

データソース

対象データは、ユーザーが明示的に設定したローカルの読み取り専用ソースです。 アプリは元データを勝手に移動・削除・公開しません。

写真画像のメタデータ、撮影日時、必要に応じた画像説明。実モデル送信前にローカルで縮小・メタデータ除去します。
LINE エクスポートテキスト形式のトーク履歴を構造化したメッセージ。
ノートMarkdown、TXT、JSON、PDF メタデータなどの個人メモ。
派生メタデータキャプション、エンティティ候補、イベント候補、注釈。
SQLite データベースローカルの構造化メタデータ保存先。
ベクトルインデックス任意の埋め込み検索用。既定テストは軽量な fake/hash 実装です。

AI エージェント構成

Private Memory Agent は、ひとつの巨大なチャットボットではなく、 役割を分けたローカル処理の組み合わせとして設計されています。

Leader Agent
質問と証拠から最終回答を作る。
Retrieval Agent
FTS、フィルタ、任意の意味検索で証拠を集める。
Photo Understanding Agent
画像説明、物体候補、OCR などを保存する。
Japanese Text Agent
LINE とノートから話題、日付、行動候補を抽出する。
Timeline Agent
時刻、場所、人候補、話題から仮説イベントを作る。
Evidence Critic
回答が既知の証拠 id に基づくか検査する。
Privacy Guard
名前や GPS などを表示前に保護する。
Local API / UI
localhost の API と最小 UI から操作する。

取り込み後、写真は必要に応じてローカルで前処理し、写真注釈もテキスト検索インデックスへ入れます。 FTS、キーワード fallback、任意のベクトル検索で証拠を取得し、 Leader Agent に渡す前に「証拠パック」として整形します。最終回答は Evidence Critic と Privacy Guard のルールを通ってから表示されます。

実モデルはローカルサーバーを手動で起動して使います。テストや基本動作は fake モデルで動くように作られており、GPU や実モデルファイルを必須にしません。

証拠に基づく回答ポリシー

回答は、次の構造を持つことを目標にしています。

conclusion証拠から言える結論。
evidence使った証拠 id と安全なスニペット。
confidence確信度。弱い証拠では低くする。
unknownsまだ分からないこと、追加確認が必要なこと。
used sources写真、LINE、ノートなど使用した種類。
unsupported claims証拠外の推測は避ける。

プライバシーとセキュリティ方針

  • local-first: 既定では外部 API に個人データを送りません。
  • 読み取り専用: 写真、LINE、ノートの元データは読み取り専用として扱います。
  • ログ制限: 私的な本文、OCR、GPS、名前、ファイル名は既定でログに出しません。
  • プロンプト注入対策: ノートや LINE 内の命令文を、システム命令として扱いません。
  • 自動本人断定なし: 顔や名前から人物同一性を自動断定せず、ユーザー確認を重視します。
  • localhost 前提: API と UI はローカル利用を前提にし、公開プロキシに出しません。

回答例（架空の例）

質問: 「先週の展示会で何を見た？」

結論: 架空の例では、展示会で新しいカメラ機材を見た可能性があります。

証拠: photos:12 の安全な画像説明、notes:5 の展示会メモ。

confidence: 0.62

unknowns: 実際に購入したかどうかは、この証拠だけでは不明です。

used sources: photos, notes

この例は完全に架空です。実在の写真、メッセージ、ノート、人物名は使っていません。

E2E smoke は既存 DB の件数、インデックス状態、証拠検索、証拠パック、構造化回答を確認します。 既定では取り込みや写真注釈を実行せず、ファイル名、フルパス、GPS、LINE 本文、ノート本文、 画像キャプション全文、クエリ本文を表示しません。

smoke が成功しても検索品質が十分とは限りません。fallback だけで成功していないかを --no-fallback と pma retrieve audit で確認します。 物理テーブル名は pma db schema で確認でき、現在のテキスト検索テーブルは text_search_documents です。手動集計用には互換 view text_documents もあります。 pma index text 実行後は、LINE、ノート、写真注釈が同じ検索診断に現れます。 日本語の長い質問は FTS だけでなくキーワード LIKE fallback でも候補数を確認します。 ノートの証拠を確認したい場合は --require-source notes を使い、 source_stage_counts.notes の候補数と drop reason を確認します。 --fake-model は実モデルを呼ばず、弱い LINE/ノート証拠では低い confidence を返すため、 Evidence Critic の検証を通して構造化回答の形だけを安全に確認できます。 実モデル確認は fake-model が通った後に pma models ping leader で endpoint を確認し、 --chat-smoke --max-tokens 64 で短い生成を確認し、 --json-smoke --max-tokens 128 で合成 JSON 応答を確認してから、 --real-model --query-limit 1 --timeout-seconds 600 --max-tokens 512 --json から始めます。 PMA は許可された evidence ID と source label を prompt に明示し、DeepSeek 系 reasoning model が <think> block、Markdown fence、JSON 前後の文章を出しても、 最初の妥当な JSON object を抽出し、 証拠 ID と used sources を Evidence Critic で検証します。 endpoint が対応している場合だけ --response-format-json で OpenAI 互換 JSON mode を要求します。 JSON が壊れた場合は既定で 1 回だけ短い repair prompt を送り、出力には raw model output ではなく response length、extraction strategy、retry 状態、brace や <think> の有無などの安全な metadata を表示します。 raw output は private content を含み得るため、明示的な --show-model-output の時だけ truncated preview として表示します。 回答本文も private evidence 由来の内容を含み得るため、既定では表示しません。 ローカルで確認する場合だけ --show-answer を付けると、conclusion、confidence、 evidence references、used sources、unknowns を表示します。証拠 snippet はこの option では表示せず、 必要な場合だけ別の --show-snippets を明示します。 JSON には answer_audit として成功数、validation error 数、retry 成功数、 confidence 平均、evidence reference coverage、source coverage を安全な集計として出します。 --show-answer や --show-snippets の出力は公開チャットへ貼り付けないでください。 256 tokens で retrieval は成功しても JSON が完了しない場合は、同じ 1 query smoke を --max-tokens 512 または --max-tokens 1024 で再試行します。 写真注釈数より text index 内の写真注釈数が少ない場合は、 pma index text の再実行を促す warning を表示します。 実モデル smoke では、既定でコンパクトな redacted evidence packet を送り、timeout、max tokens、 prompt size、送信した証拠件数を安全な診断として表示します。

回答品質を継続的に見る場合は configs/golden_questions.example.yaml を雛形にし、 private な質問は Git から除外される configs/golden_questions.local.yaml に置きます。 pma eval golden は retrieval-only、fake-model、real-model の順で確認でき、 retrieval 成功、回答成功、証拠件数、source coverage、confidence、unknowns、 JSON retry、validation error、privacy-safe output を質問ごとに集計します。 Markdown report には answer_correctness、evidence_relevance、source_coverage、 uncertainty_handling、privacy_safety、source_policy_passed、source_mismatch_notes、 irrelevant_evidence_notes、notes の手動採点欄を用意します。 golden question には expected_sources、required_sources、preferred_sources、 excluded_sources、expected_keywords、optional_keywords、negative_keywords、evaluation_focus を書けます。 --source-policy strict では expected/required source の不足を評価失敗として扱い、 既定の soft では不足を診断として記録します。excluded source は golden retrieval から除外します。 source coverage は十分でも evidence relevance が弱いことがあるため、expected/optional keyword を retrieval query に足し、 keyword を含む証拠を boost し、negative keyword を含む証拠を減点します。 report には expected keyword hit、missing keyword、negative keyword hit、 per-evidence keyword hit count、relevance score を raw evidence なしで表示します。 一回限りの確認には --expected-keyword、--negative-keyword、 --keyword-policy strict を使えます。 さらに --leader-plan を使うと、local Leader model が質問から intent、specific/generic concept、 source preference、retrieval query、acceptance criteria を持つ RetrievalPlan を作ります。 既定では plan 本文は表示せず、plan_created、query count、entity/concept count などの安全な集計だけを出します。 --leader-rerank は plan-aware な deterministic relevance judge で generic-only evidence を下げ、 specific concept に合う evidence を上げます。弱い検索には --retrieval-repair 1 で追加 query を試せます。 8-L では candidate evidence があることと usable evidence があることを分け、 candidate_retrieval_succeeded、usable_evidence_succeeded、 final_relevance_score、relevance_policy_passed を report に出します。 すべてが generic-only の場合は高い relevance score にせず、 --minimum-relevance-score、--require-usable-evidence、 --relevance-policy strict で品質 gate として失敗させられます。 8-M では repair query を specific concept と main entity から作ることを優先し、 generic-only な repair を避けます。さらに --semantic で保存済み hash embedding を使った local semantic retrieval を E2E/golden の検索に混ぜられます。 8-N では ruri-v3-310m、bge-m3、qwen3-embedding-0.6b などの local embedding alias を config 経由で解決し、明示的に pma index embeddings --model ruri-v3-310m --source line --source notes を実行した場合だけ real embedding を作ります。必要なら --reranker ruri-v3-reranker-310m も選べます。 report には semantic_candidate_count、repair_specific_query_count、 repair_generic_query_count、semantic_embedding_model_id、 reranker_model_id などの安全な件数と ID だけを出します。 8-O の pma eval semantic-compare は text-only、hash semantic、real semantic、 reranker、Leader plan ありの構成を比較します。candidate が増えただけの構成は quality_judged=false として扱い、Leader relevance judge が走った構成だけを usable evidence quality の推薦候補にします。CUDA driver warning が出る場合は --embedding-device cpu を指定できます。 --show-plan と --show-relevance は local-only の明示的な診断です。 relevance を見る必要がある時だけ --show-snippets --snippet-chars N を明示します。 既定では質問本文、回答本文、snippet、raw evidence、raw model output を表示しません。 --show-answer や --show-snippets を使った report は private output として扱い、 公開チャットへ貼り付けないでください。

9-A では pma api serve --config configs/paths.local.yaml --host 127.0.0.1 --port 8787 で起動する localhost UI を evidence-first agent console に更新しました。 http://127.0.0.1:8787/ui では質問、retrieval-only / fake-model / real-model、 leader plan、leader rerank、semantic retrieval、reranker、retrieval repair、strict relevance、 show_answer、show_snippets を切り替えられます。画面は POST /api/chat/query と GET /api/system/status を使い、CLI を shell out せず既存 E2E retrieval path を呼びます。 9-A2 では chat UI として使いやすいように、ローカル UI では回答本文を既定で表示します。 ただし raw evidence snippet、raw model output、LINE 本文、ノート本文、写真 caption、 OCR、ファイル名、フルパス、GPS、EXIF は既定では表示しません。 show_answer を外すと metadata-only になり、回答が生成済みでも非表示であることを明示します。 show_snippets は引き続き明示操作で、snippet は truncated/redacted されますが private output として扱います。回答や snippet に private な内容が含まれる場合は公開チャットへ貼り付けません。

9-E では chat UI の evidence viewer を改善しました。長い evidence ID は折り返し可能な chip/list として表示し、 temporal event query の candidate date は展開可能な card で表示します。card には date、confidence、 photo count、annotation count、LINE/notes support count、reason summary、supporting evidence を出します。 展開後は Photos、LINE、Notes、Rejected / Weak evidence の local tab で確認できます。 outing_annotation_keyword のような machine reason code は内部に残しつつ、 UI では「外出を示す可能性のある注釈があります」のような日本語 label も表示します。 写真 evidence は media_item_id だけを受け付ける localhost thumbnail endpoint から小さな preview を表示できます。 backend は任意の filesystem path を受け取らず、thumbnail response に filename、full path、GPS、EXIF、OCR を含めません。 LINE/notes snippet と photo annotation summary は show_snippets を明示した場合だけ truncated 表示され、 read-more で local に展開できます。 show_full_text と raw model output は既定 OFF です。

9-B では 2025年12月で出かけたのはいつ？ のような temporal event query を、 通常のキーワード検索だけに頼らず扱います。明らかな年月表現、 去年12月、先月、去年の夏 を日付範囲に変換し、 capture timestamp として保存された media_items.taken_at で写真候補を読みます。 写真注釈と安全な metadata から外出らしさを score し、日別に cluster して、 高そうな日には同日の LINE/ノート件数と evidence ID を補助情報として付けます。 UI では candidate date、confidence、photo/LINE/note の evidence ID を表示し、 used evidence、examined candidate、weak/rejected evidence を分けます。 should_use=false の候補は answer evidence として扱いません。 既定ではファイル名、フルパス、GPS、LINE 本文、ノート本文、OCR、写真 caption 全文は表示しません。

temporal event query が写真の日付で動くには media_items.taken_at が必要です。 9-C0 では pma media timestamps audit で taken_at の有無、実ファイル存在数、 EXIF/XMP/video/filename から抽出可能な件数、unsupported format、parse error、 任意の month histogram を path なしで確認できます。 大きなライブラリでは抽出可能性の確認は既定で sample に制限し、全件 deep audit は --extract-limit 0 を明示した時だけ行います。 pma media timestamps backfill --dry-run --limit 20 --method auto は source file を read-only のまま調べ、書き込み候補数だけを返します。 backfill は既定で dry-run です。audit/backfill は --db が無い場合、 configs/paths.local.yaml の storage.sqlite_path を使います。 ローカル SQLite DB を backup し、件数を確認した後に --apply を明示した時だけ SQLite metadata に taken_at を書き込みます。 既存の --write は alias として残していますが、推奨は --apply です。 長い実行では --commit-interval ごとに commit するため、最後まで全更新を保留しません。 source photo/video file 自体は変更しません。 exiftool があれば JPEG、HEIC、MOV、MP4、XMP を優先し、 なければ Pillow で画像 EXIF を読みます。file mtime は低 confidence の fallback なので、 --fallback file-mtime を明示した時だけ使います。 DB には timestamp source、confidence、timezone 情報を保存し、既存の高 confidence timestamp は 既定では上書きしません。

9-C では temporal query が unknown になった時の診断を増やしました。 pma query "2025年12月で出かけたのはいつ？" --temporal-diagnostics は、 parsed date range、date range source、対象の時間表現、timezone、taken_at coverage、 写真候補数、annotation 済み/未済み数、media type filter 前後の件数、近傍月の写真件数を返します。 写真候補が無い、または弱い時は、同じ日付範囲の LINE/ノートから外出に関係しそうな語句を count-only で探し、 evidence ID と source count だけを返します。写真が無くても LINE/ノート候補がある場合は、 その日付を弱い fallback evidence として示し、写真で確認できていないことを明記します。 既定では LINE 本文、ノート本文、caption、OCR、ファイル名、フルパス、GPS、EXIF は表示しません。

制限事項

  • 証拠を超えて推測するべきではありません。
  • 画像理解モデルは写真を誤読する可能性があります。
  • LINE エクスポート形式の違いにより、解析が完全でない場合があります。
  • 人物同一性、特に顔と名前の対応はユーザー確認が必要です。
  • 健康、法律、金銭、人間関係などの敏感な結論は慎重に扱う必要があります。
  • 実モデルの品質、速度、VRAM 使用量はローカル環境と起動方法に依存します。
